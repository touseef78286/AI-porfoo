# Database Design

Status: **Phase 1 migration 0001 implemented and tested for the discovery tables. Later tables are not created yet.**
Last updated: 2026-11-04

## 1. Storage decision

- Engine: SQLite.
- Access: a narrow adapter around Node's `node:sqlite` for Phase 1.
- Location: configurable private data directory, gitignored; during development on `T:`.
- No database file in source control.
- No local database exposed to the public application.

The built-in module is experimental on the verified Node.js runtime. All SQL and lifecycle behavior must remain behind the adapter so a stable driver can replace it without changing domain code.

## 2. Connection settings

On open:

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
```

Additional rules:

- One writer connection per process; short transactions.
- Read queries may share the connection with serialized access in Phase 1.
- WAL checkpoints on a bounded schedule or after large scan writes.
- `VACUUM INTO` for backups; retention is bounded.
- No user-provided SQL.
- All statements parameterized.

## 3. Conventions

- Table names: plural snake_case.
- Timestamps: ISO-8601 UTC text, with a numeric epoch alternative only if measured necessary.
- Primary domain IDs: UUID v7 strings generated by the application.
- Foreign keys enforced.
- Every mutable row has `created_at` and `updated_at`.
- Soft lifecycle states are explicit; historical rows are not silently deleted.
- JSON columns are validated before storage and used only for evidence/extension data, not core relational queries.
- `schema_migrations` records applied versions.

## 6. Migrations

Location (implemented): `apps/agent/src/db/migrations/NNNN_name.sql`.

Rules:

- Applied in a transaction where SQLite permits.
- Checksums stored; edited applied migrations are rejected.
- Back up before destructive or schema-changing migrations.
- Startup stops on migration failure.
- No automatic destructive downgrade.
- Test migration from an empty DB and from the previous schema.
- Export/restore test required before Phase 1 acceptance.

## 7. Backup and recovery

- Pre-migration and daily-once backup policy.
- `VACUUM INTO` to a timestamped file in a private backup directory.
- Keep a small bounded number of backups.
- Verify a restore into a temporary file.
- Never include backup files in public output or Git.
- Document the restore procedure in the operational README when implemented.

## 8. Data retention

- Deleted/missing projects remain as historical records until explicitly purged.
- Scan errors may be pruned after a configurable retention period.
- Publication history should be retained; it contains approved public data only.
- Do not retain raw manifest contents once extracted fields are stored.
- No source code, secret values, or full dependency lockfiles are stored.

## 9. Public separation

The public application has no database connection to the local DB. Publication uses a separate validated payload and snapshot file. The public schema is versioned independently.

## 10. Verification requirements

Phase 1 must verify:

- Migrations apply from empty state.
- Foreign keys are enforced.
- WAL mode is active.
- Transaction rollback works.
- Duplicate project paths are rejected.
- Scan history and errors persist.
- Backup and restore work with the chosen SQLite API.
- No sensitive fixture value appears in any table.

No schema claim in this document should be treated as implemented until those checks exist.

## 11. Implementation status — Phase 1 Gate 3

Implemented in `apps/agent/src/db/`:

| Component | File | Behavior |
|---|---|---|
| Connection adapter | `connection.ts` | Opens `DatabaseSync`, applies the four approved pragmas, creates the parent directory, exposes `withTransaction` |
| Migration runner | `migration-runner.ts` | Loads contiguous migrations, verifies SHA-256 checksums, applies each in a transaction, rolls back failures, rejects edited or absent migrations |
| Migration 0001 | `migrations/0001_discovery_schema.sql` | Creates the Phase 1 discovery tables |
| Backup/restore | `backup.ts` | `VACUUM INTO` snapshot, integrity inspection, restore into a new file, refuses overwrites |

Tables created by migration 0001: `project_roots`, `projects`, `project_identities`, `detection_evidence`, `technologies`, `project_technologies`, `dependencies`, `scan_runs`, `scan_errors`, `exclusions`, `project_overrides`, `project_status_history`, plus `schema_migrations` managed by the runner.

Known limitations:

- `node:sqlite` is experimental on Node 24.11.0 and emits `ExperimentalWarning`; the adapter isolates it.
- `VACUUM INTO` requires the target file to be absent; callers must generate unique backup names.
- No runtime database file is created yet. Tests use in-memory databases and workspace temp files under `.cache/test-tmp`.
- Schema foreign keys are enforced at connection level; any future connection bypassing `openDatabase` would lose that guarantee.
